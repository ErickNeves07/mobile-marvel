# 026 — Gauntlet and variant progression — Design

Use the existing Forge SQLite database. Schema version 4 adds a singleton Gauntlet state, a `(character_id,tier_id)` ownership table, and one equipped-tier row per character. Migration preserves Forge and campaign data. Activation checks all six complete counts in one transaction and sets a durable flag without decrementing inventory. Variant unlock checks activation, catalog IDs, the next owned tier and required Stone's complete count; event keys are unique and writes atomic. Equip only accepts an owned tier. The repository does not hardcode the roster: a character's origin ownership/equipment rows are created idempotently when its chamber state is first read after Gauntlet activation. Before activation, collection displays all tiers locked and no equipped tier.

The UI extends Forge with a Gauntlet/Chamber section and Collection with per-character tier actions. Tier labels/names remain sourced from the shared catalog. Each of five tiers uses its corresponding first five Stone requirements: Space, Mind, Reality, Power, Time; Soul is needed to activate the Gauntlet. These relationships are a reversible derived design choice based on matching six Stones to five variant tiers plus the Gauntlet gate. Duplicate unlock for another character never consumes more Stone.

All repository writes run on the existing executor. No Comic Vine/editorial data, provider, network, new dependency, gameplay stat or AI is used. Tests cover Stone gate, zero consumption, tier order, duplicate idempotency, equip validation, cap/rollback and schema migration.
